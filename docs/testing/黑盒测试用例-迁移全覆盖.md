# BlackBoxPro 黑盒测试用例（迁移后全覆盖）

## 1. 目标

本文先定义“要测什么”和“怎么算通过”，用于后续落地 GitHub Actions、本地黑盒脚本和夹具补齐。

本轮覆盖四条测试线：

| 测试线 | 版本 / 载体 | 传输协议 | 目标 |
|---|---|---|---|
| 联调线 A1 | `1.21.11` Fabric 客户端 + 服务端插件 | HTTP dual mode（Plugin 38080 ↔ Mod 38081） | 验证 Fabric loader 下 action、query、screenshot 的整链路 |
| 联调线 A2 | `1.21.11` NeoForge 客户端 + 服务端插件 | HTTP dual mode（Plugin 38080 ↔ Mod 38081） | 验证 NeoForge loader 下 action、query、screenshot 的整链路 |
| 联调线 B | `1.12.2` Forge 客户端 + 服务端插件 | HTTP dual mode（Plugin 38080 ↔ Mod 38081） | 验证兼容版本的整链路与动作子集 |
| 纯客户端线 C | `1.21.11` NeoForge `runClient` | 直连 Mod HTTP `127.0.0.1:38081/execute` | 验证纯 mod 客户端 action、世界管理 action、HTTP 协议稳定性 |

> **协议说明（v1.4 迁移后）**：所有通信已从 Plugin Message Channel 迁移为 JDK 内置 HttpServer，零依赖。测试脚本统一 POST `/execute`，服务端返回 ResponseMessage（有请求必有响应原则）。`run_test` 接口阻塞直到测试完成，响应包含完整结果。

说明：

- 当前仓库主干已明确实现 `1.21.11` Fabric / NeoForge 与 `1.12.2` Forge 的 action catalog 与协议链路。
- 纯客户端线 C 的 `create_world` / `join_world` / `leave_world` / `query_world_state` 按 `1.21.11` NeoForge 目标接口编写，后续接入 HTTP runner 后直接执行。
- `1.21.11` 如果同时发 Fabric / NeoForge 两个客户端产物，则联调线 A 应在两个 loader 上各跑一轮。
- `1.12.2` 联调用例只跑支持的 action 子集，遇到纯客户端世界管理类动作必须标记为 `skip`。

## 2. 统一通过标准

### 2.1 协议层通过标准

所有协议用例都要满足：

1. 请求成功到达目标入口。
2. 响应 `id` 与请求 `id` 一致。
3. 响应 `status` 只能是 `success` 或 `failure`。
4. 失败时必须返回可读 `message`，且后续请求仍可继续执行。
5. 不能因单个异常 action 导致客户端崩溃、断线、卡死或协议通道失效。

### 2.2 Action 层通过标准

所有 action 用例都要满足：

1. action 被正确路由到对应执行器。
2. `success` 时客户端状态变化与 action 语义一致。
3. `query_*` 类 action 必须返回结构完整、字段可断言的 `data`。
4. `screenshot` 必须返回 `data.filePath`。
5. 长耗时 action 不能依赖不可控固定 `sleep` 才能稳定通过，必须以状态达成作为完成标准。

### 2.3 回归通过标准

1. 同一轮执行后，协议通道仍可继续收发。
2. 重复执行同一 action 不应导致状态泄漏或夹具污染。
3. 同版本全量执行完成后，截图、日志、响应文件可定位到每个 case。

## 4. 传输协议测试用例

### 4.1 Plugin Message 联调协议

适用版本：`1.21.11`、`1.12.2`

| 用例 ID | 标题 | 步骤 | 预期 |
|---|---|---|---|
| `PROTO-PM-001` | 通道注册成功 | 启动服务端与客户端，观察服务端 `ChannelHandler.enable()` 与客户端 `NetworkHandler.register()` | 两端都完成 `blackbox:command` / `blackbox:response` 注册，无异常日志 |
| `PROTO-PM-002` | 基础请求-响应闭环 | 服务端发送 `query_player_state` | 客户端收到 command，返回同 `id` 的 success response |
| `PROTO-PM-003` | JSON 编解码一致性 | 分别发送空参数、标量参数、对象参数、数组参数（通过 `batch`） | 两端 UTF-8 JSON 解码一致，字段不丢失 |
| `PROTO-PM-004` | 缺少 `action` 的坏包处理 | 手工发送缺少 `action` 的 command JSON | 客户端返回 `failure`，`message` 含 malformed/missing action，通道继续可用 |
| `PROTO-PM-005` | 非法参数容错 | 发送参数类型错误或缺失的 action | 返回 `failure` 或业务失败信息，不崩溃、不掉线 |
| `PROTO-PM-006` | 超时回收 | 发送一个预期不会返回的请求或中途断开客户端 | 服务端 future 在 `response-timeout-ms` 后失败完成，`pending callback` 被清理 |
| `PROTO-PM-007` | 超大 payload 限制 | 构造超过 `max-payload-size=32767` 的请求 | 服务端拒绝发送并记录 warning，请求最终按超时失败处理 |
| `PROTO-PM-008` | 连续 100 次短请求稳定性 | 连续发送 `query_player_state` / `keep_alive` / `wait` | 无丢响应、无串包、无重复 `id`、无内存泄漏迹象 |
| `PROTO-PM-009` | 批处理顺序一致性 | 发送 `batch[sneak_start, wait, sneak_stop]` | 客户端顺序执行，最终状态与动作序列一致 |
| `PROTO-PM-010` | 单次失败不污染后续请求 | 先发一个必失败 action，再发 `query_player_state` | 第二个请求仍正常成功 |

1. 准备对应夹具。

## 6. 纯客户端世界管理与 Action 用例

适用版本：`1.21.11 NeoForge runClient`

说明：

- 这一组针对迁移后的纯客户端线。
- 完成标准不能靠固定 `sleep`，必须以“真的进入世界 / 真的回到主菜单 / 真的重新进入世界”为准。

| 用例 ID | 标题 | 步骤 | 预期 |
|---|---|---|---|
| `LOCAL-001` | 主菜单态查询 | 启动 `runClient` 后调用 `query_player_state` | 返回主菜单态或 failure，但语义稳定且可区分“未进世界” |
| `LOCAL-002` | 创建世界 | 调用 `create_world` | 真正进入新世界，后续 `query_world_state` 成功 |
| `LOCAL-003` | 世界内查询 | 世界内调用 `query_player_state`、`query_world_state` | 两者都成功，字段完整 |
| `LOCAL-004` | 退出世界 | 调用 `leave_world` | 真正回到主菜单，HTTP 继续可用 |
| `LOCAL-005` | 重新进入已有世界 | 调用 `join_world` | 真正进入指定已有世界 |
| `LOCAL-006` | 进入不存在世界失败 | 对不存在或损坏世界调用 `join_world` | 返回 failure，且仍停留在主菜单 |
| `LOCAL-007` | 菜单态误调用世界内 action | 在主菜单执行世界内 action | 返回 failure，不崩溃 |
| `LOCAL-008` | 世界切换稳定性 | 执行 `create_world -> leave_world -> join_world -> leave_world` | 每一步都完成，状态不串 |
| `LOCAL-009` | 客户端关闭后的端口行为 | 关闭 `runClient` 后再请求 HTTP | 连接失败或返回不可用，但无假成功 |
| `LOCAL-010` | 异常请求后恢复 | 先发非法 action，再发合法 query | 第二个请求仍成功 |

## 7. 执行顺序建议

建议按下面顺序推进自动化：

1. 先打通 `PROTO-*`，确认 1.21.11 Fabric / NeoForge 与 1.12.2 Forge 的协议链路稳定。
2. 再做 `ACT-QUERY-001` 与 `ACT-CLIENT-001`，它们最容易给后续动作提供断言能力。
3. 然后补 `FX-BLOCK` / `FX-ENTITY` / `FX-GUI`，把 `ACT-BLOCK-*`、`ACT-ENTITY-*`、`ACT-CONTAINER-*` 接进来。
4. 最后收口 `ACT-ADV-*`、`ACT-DEBUG-*`、`LOCAL-*` 这三组高波动用例。

### 9.4 可疑项备注

#### ⚠️ `query_block_state` 返回 air

- 查询坐标：`ctx.fixtureManager.block(0, -1, 0)`，玩家 y=166.5 → 坐标 y=165
- 计算逻辑：`floor(166.5) - 1 = 165`，而玩家实际站立地板块在 y=166（占据 166→167）
- **结论**：坐标计算偏移了一格，查到的是地板下方的空气，而非地板本身。测试"通过"是因为 verify 只检查 data 非空，实际断言存在盲区。
- **建议**：`fixtureManager.block(0, 0, 0)` 或 `block(0, -1, 0)` 语义需明确，或改为查询玩家正下方实体碰撞区。

#### ⚠️ `query_screen_state` 返回 `GuiIngameMenu`

- 返回 screenClass=GuiIngameMenu（暂停菜单），而非正常游戏态 HUD
- **可能原因**：前序截图操作触发了截图快捷键后游戏转入暂停；或客户端在某次 reset 时打开了菜单
- **建议**：在 `resetBaseline()` 中加入 `close screen` 逻辑，确保每次测试开始前屏幕状态为游戏态
